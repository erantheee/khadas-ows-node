# A2DP sink on the Edge2 (received audio for the relay box) — 2026-11-10

Status: **software path verified end-to-end on the board with a Mac as A2DP source**;
phone pairing/listening is still a human step. This is the P0-5 item from
[docs/khadas-npu-box-embedded-plan.md](../../cores3-noise-adapt-demo/docs/khadas-npu-box-embedded-plan.md)
(that file lives in the other repo) — "A2DP sink (BlueZ+PipeWire) + latency".

## What the board can/cannot do (hardware boundary)

| Fact | Evidence |
| --- | --- |
| AP6275P combo (Broadcom BCM43752), BT over HCI-UART, HCI 5.1, `br/edr` + `le` | `btmgmt info`, MAC `40:D9:5A:63:8B:53` |
| Classic BT (A2DP) is available; **CoreS3/ESP32-S3 is not** (BLE only) | this board is the Edge2; no firmware change involved |
| Playback devices on this image: **DP and HDMI only**, no analog 3.5 mm codec | `aplay -l` (cards `rockchip-dp0`, `rockchip-hdmi0`) |
| Capture: PDM mic array `hw:2,0` (used by `dmic_evidence.py`) | `arecord -l` |

Consequence: "A2DP sink + 板载 codec output" (P0-5) can be split in two — the A2DP
ingress is done here; the analog codec output is **not available on this Edge2 image**
and still needs either an I2S codec overlay or the 2.4G/earbud path.

## What is configured (run `tools/a2dp_sink_setup.sh`, idempotent)

1. Packages: `pipewire pipewire-pulse wireplumber libspa-0.2-bluetooth
   pulseaudio-utils bluez-tools` (Ubuntu 24.04: PipeWire 1.0.5, WirePlumber 0.4.17,
   BlueZ 5.72). BlueZ only advertises A2DP UUIDs while a media endpoint provider
   (PipeWire/WirePlumber) is connected — before this the adapter showed only
   AVRCP UUIDs and no A2DP sink.
2. Adapter class and pairing policy in `/etc/bluetooth/main.conf`:
   `Class = 0x240414` (major: Audio/Video, minor: loudspeaker),
   `DiscoverableTimeout = 0`, `PairableTimeout = 0`.
   Observed class after restart: `0x006c0414` while discoverable (BlueZ adds the
   discoverable + service-class bits). Without the audio class macOS still paired
   but classified the box as an unknown device.
3. Persistent pairing agent: `bt-agent -c NoInputNoOutput` as
   `/etc/systemd/system/bt-agent.service` (enabled). This is what lets a phone pair
   without a screen/keyboard on the box; `bluetoothctl`'s agent only lives as long as
   the interactive session.
4. User audio session that survives SSH logout/reboot: `loginctl enable-linger khadas`
   + `systemctl --user enable --now pipewire.socket pipewire-pulse.socket
   wireplumber.service`.
5. **Keep HFP/HSP roles enabled** (WirePlumber default). Do *not* restrict
   `bluez5.roles` to A2DP only: with A2DP-only roles macOS 26 never published the box
   as an audio device — `coreaudiod` logged
   `BTUnifiedAudioDevice: All profiles not connected, delay publishing`, the A2DP
   transport stayed `idle` and no PCM reached the box. With the default roles the
   device is published immediately and macOS streams SBC.

## How the received audio is exposed

After a source device streams to the box, PipeWire creates
`bluez_input.<source-mac>.<n>` (`media.class = Stream/Output/Audio`, `S16LE 2ch
44100`, quantum 512) and — by default WirePlumber policy — links it to the default
sink (HDMI on this image). The received PCM is therefore available on that sink's
monitor:

```text
bluez_input.<MAC> -> default sink (HDMI) -> <sink>.monitor  --parec--> WAV
```

`tools/a2dp_sink_capture.sh --seconds 10 --out /tmp/a2dp.wav` records it;
`--probe` records 3 s and prints peak/RMS and whether the capture is digital silence.
This is a bench/prototype tap, not the final integration: the next step is to feed
the same PCM into `worker.py`/the node instead of the network stream from the Mac.

Note on naming: the card profile shown for a *receiving* connection is
`audio-gateway: Audio Gateway (A2DP Source & HSP/HFP AG)` — that is PipeWire's
receiving-A2DP mode (remote = source), not an HFP audio-gateway mode. Do not read
"sinks: 0, sources: 0" in `pactl list cards` as "no audio path"; the node is created
dynamically when the transport starts and is a `Stream/Output/Audio` node.

## Verification evidence (board, 2026-11-10 ~07:4x–07:5x UTC)

1. Adapter: `bluetoothctl show` → `Class: 0x006c0414`, `Discoverable: yes`,
   `Pairable: yes`, 10 UUIDs including `Audio Sink (110b)`, `Audio Source (110a)`,
   AVRCP Target/Controller, Handsfree + Handsfree Audio Gateway.
2. Pair from a Mac with the service agent (fresh pair, no manual agent): paired +
   connected; macOS published "Khadas" as an audio output (2 ch) and streamed SBC.
3. `pactl list cards` → `bluez_card.A0_9A_8E_50_A3_35`, profile `audio-gateway`;
   BlueZ `MediaTransport1` with UUID `110b` (Audio Sink = we receive), codec byte `0`
   (SBC); macOS log: `Configuring A2DP audio device ... MTU=672, RTP_len=656`,
   `Successfully opened streaming channel`, `Starting A2DP audio streaming`.
4. Tone check: played 1 kHz from the Mac, captured the sink monitor on the board →
   1 kHz band +40.5 dB over the floor, dominant FFT bin `1000.0 Hz`, peak `0.089`
   (≈ −21 dBFS). Digital silence when nothing streams.
5. Latency (method and numbers in `docs/evidence/a2dp-sink-20261110.json`):
   NTP-style UDP clock offset Mac↔board (best-RTT median **−0.8 ms**, best RTT
   8.5 ms); a `pw-play` click marker in the same capture anchors the board timeline;
   nine consecutive 1 kHz beeps (1 s period) give elapsed-since-`afplay`-spawn =
   16.424…24.424 s → **424.3 ms** modulo the 1 s beep period, identical for all nine
   (stdev 0.0 ms). So: **from `afplay` spawn to PCM consumed at the board sink ≈ 424 ms**
   (includes macOS player start, encode, BT transport, board jitter buffer and
   44.1→48 kHz resample). macOS-side framing measured 512-frame HAL buffers
   (11.6 ms @44.1 kHz). Caveat: measured with a Mac as source, not with a phone;
   the true latency is 424 ms + n·1 s, n=0 is the plausible branch (player + A2DP
   cannot plausibly exceed 1 s, and the stream-open transient was excluded because the
   stream was already running).
6. Persistence: after `systemctl restart bluetooth` the adapter came back with
   `Discoverable: yes`, `Pairable: yes`, 10 UUIDs incl. Audio Sink; `bt-agent.service`
   active; PipeWire/WirePlumber/pipewire-pulse active. (Full power-cycle not tested —
   the board is in live-demo use; `@reboot` cron from the earlier session is untested.)


## Listening through wired earphones (USB DAC) — verified

The Edge2 has **no usable analog audio output**: the device tree contains an `es8316-sound`
card, but the codec is not populated on this board (`dmesg: es8316 3-0010: ES8316 doesn't
exist, exit of probe!`; I2C bus 3 has no device at 0x10) and `aplay -l` only shows DP/HDMI.
The kernel does have `CONFIG_SND_USB_AUDIO=y`, so a **USB DAC / USB-C earphone is the way to
listen**: plug it in, select it as the default sink, and WirePlumber links each received A2DP
stream to it automatically:

```text
phone --A2DP--> bluez_input.<phone-mac> --policy link--> USB DAC sink --3.5mm--> earphone
```

Verified 2026-11-10 with a phone (Android, `oowow`) as source and a USB DAC (KT/Moondrop
"Old Fashioned", USB id `35d8:0122`) with a wired earphone: board-side
`pactl list sink-inputs` showed `Sink Input #889 ... media.name = "oowow (codec SBC)"` on the
USB sink, `s16le 2ch 44100Hz`, sink state RUNNING, and `pw-link -l` showed the two links
created by policy without any manual `pw-link`. Captured 6.14 s of the USB sink monitor:
RMS **-40.5 dBFS** (music, not silence), peak 0.042. USB DAC adds only ~10-20 ms locally; the
phone->board leg dominates (Mac source measured 424 ms; the phone leg was not directly
measured, expect the same order) -> **≈0.4-0.5 s end to end**, fine for music, not for video
lip-sync.

Select the USB sink after plugging/replugging it:

```bash
sh tools/a2dp_sink_usb_output.sh     # first USB sink -> default output, unmute, 85 % volume
```

The default sink is saved in WirePlumber state, so a stable plug stays the default.

Consequence for the product plan: the "板载 3.5 mm codec output" assumption for Edge2 does not
hold — a box that must drive wired earphones needs an added codec or a USB-Audio-class device.


## NPU relay: A2DP in -> board stem/envelope -> USB earphone (verified with live music)

`tools/a2dp_stem_relay.py` closes the loop: it captures what the A2DP sink receives, sends
it through the board's own C++ node + NPU worker (`127.0.0.1:9100`, `--mode npu`,
`--policy s3`, `--output-mode envelope`) and plays the processed stream to the USB DAC.

```text
phone --A2DP--> bluez_input.<mac> --> silent sink "a2dp_stem_in"
                                            |  parec 44.1 kHz float32
                                            v
                                relay ==TCP 9100==> node --> NPU worker
                                            ^
                              processed PCM (float32 44.1 kHz)
                                            v
                              pacat --> USB DAC --> wired earphone
```

Why the silent intermediate sink: the A2DP stream must not go directly to the earphone,
otherwise the direct and processed copies would mix. The relay makes the null sink the
default and runs a **route guard** that moves any A2DP sink-input back onto it (WirePlumber's
stream-restore otherwise re-links the stream to the earphone sink it used before — observed
on this board).

### Verified on the board (2026-11-10, phone as source, real music, 240 s run)

| Quantity | Value |
| --- | --- |
| relay chunks / played audio | 239 chunks = 238 s, `captured_audio_seconds` = 235 s (music from 1 s in) |
| underruns / dropped chunks | **0 / 0** |
| request RTT | p50 **373 ms**, p95 **416 ms** (rtf 0.34–0.42) |
| node | `actual_mode=npu` throughout, 0 fallbacks, `last_rtf` 0.37 |
| audio A/B vs input monitor | 24-band output/input gain **0.0 dB** in every band |

The 0 dB A/B is **expected in this quiet room**: the board tuner reports
`mode=FLAT, applied_peak_db=0.0` with `dmic_level_dbfs=-60.6, environment=QUIET`, so the
envelope layer is transparent (the NPU still runs masks and reconstruction; the output is
the reconstructed mix at unity gains). Audible envelope/masking effects need a noisy
environment (or a forced scenario / injected evidence), and that is the known DMIC-level
calibration gap, not a relay bug.

* Added latency over direct playout (estimate, not acoustically measured): A2DP ~0.4 s +
  1 s capture window + ~0.4 s NPU RTT + 1 s pre-roll ~= **2.5-3 s** from phone press to
  earphone. `--preroll 1` is the minimum that held up; 0 underruns in 4 minutes.

### Usage (board)

```bash
~/khadas-ows-node/.venv/bin/python tools/a2dp_stem_relay.py --duration 600 \
    --record /tmp/processed.wav --stats-json /tmp/relay.json
```

Notes:
- the C++ node serves **one audio client at a time** — while the relay runs, the Mac-side
  five-stem bridge cannot use port 9100;
- `pacat`/`parec` are pulse-compat; `--record` writes a 32-bit-float WAV of the processed
  stream for evidence;
- the relay restores the previous default sink and removes the null sink on exit.


### Noise-triggered tuning (verified, same relay)

The 0 dB A/B above was a *quiet-room* result. With the same relay running, the user brought a
noise source close to the board's PDM mic while the phone kept streaming. The tuner switched
from `FLAT` to `SONG_EQ` within ~2 s of the DMIC level rising from -60 to -39 dBFS:

| Time (UTC) | Mode | applied | masking | lifted/cut | exposure | DMIC | env |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 09:19:43 | `SONG_EQ` | **2.17 dB** | 0.76 dB | 18 / 3 | 0.345 | -39.6 dBFS | NOISY |
| 09:20:29 | `SONG_EQ` | 1.25 dB | 0.55 dB | 18 / 6 | 0.292 | -41.6 dBFS | NOISY |
| 09:15:55 | `EXTERNAL_VOICE_INTENT` | 3.0 dB | 0.09 dB | 24 / 0 | 0.016 | -52.1 dBFS | VOICE |

Long-run numbers for that 900 s session: 899 chunks, **0 underruns**, RTT p50 309 ms / p95
393 ms, `actual_mode=npu` throughout, 0 fallbacks, 326 s of music processed, `--preroll 2`.
A windowed input/processed comparison shows +1.5..+3.5 dB band differences in the noisy
period (vs 0.0 dB quiet); that A/B is rough because the two captures are independent streams,
so the authoritative evidence is the tuner telemetry plus the human listening check — the user
confirmed the processed audio changed audibly once noise was present.

Detail: the noise source was classified as `keyboard` events (white/rain-like noise), so the
tuner used the SONG_EQ + masking path; that classification is a knob to revisit if such noise
should be treated as `wind`/other.

## Open items / risks

1. **Phone pair + listen is still a human step** (iPhone/Android → "Khadas" → play).
   The Mac result proves the box side; phone-side A2DP stacks can differ (codec
   preference, volume, reconnect behaviour).
2. **Phone path verified for playback only**: forward chain works (phone -> board -> USB DAC ->
   wired earphone) but the phone->board latency was not measured directly (no phone-side
   timestamp); use the Mac 424 ms number as the A2DP-ingress reference.
3. **SBC only** in this run. No AAC/LDAC endpoint was offered by this PipeWire build
   (macOS negotiated SBC at 44.1 kHz). That is the main audio-quality question for
   the relay box; check `pw-cli`/`bluez5.codecs` and macOS's chosen codec per session.
4. **Codec/latency for the product path** (`A2DP in + 2.4G out`) is not measured;
   only the A2DP ingress is. A2DP *source* (box → earbuds) is out of scope here.
5. **DMIC coexistence**: enabling PipeWire makes WirePlumber enumerate the PDM array;
   in this run `arecord -D hw:2,0` (`dmic_evidence.py`) stayed healthy (evidence age
   50–106 ms throughout) after one stack restart during package install. If the demo
   logs `Device or resource busy`, add the WirePlumber rule in
   `tools/a2dp_sink_setup.sh` (bottom) to disable the PDM card.
6. Discoverable/pairable are left on permanently for bench use; revert with the
   "Undo" block at the top of `tools/a2dp_sink_setup.sh` before any field test.
7. `pactl`/`parec` are the bench tools; the final integration should talk PipeWire
   (native, no pulse compat) or consume the node directly.
